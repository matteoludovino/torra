# Deploying Torra

Free tiers throughout: PostgreSQL on **Neon**, the API on **Render** (Docker), the web app on **Vercel**,
payments on **Stripe in test mode**. The order matters: the database first, then the API (its container
applies migrations on start), then the web app, then the URLs each side needs about the other, and last
Stripe's webhook, which needs the API's address.

Secrets are pasted into each provider's dashboard and nowhere else: not in the repository, not in chat.

## 0. Stripe: two sandboxes

In the Stripe Dashboard, create two **Sandboxes** (Settings → Sandboxes): one for **production** (the public
demo) and one for **development and CI**. Two, so `stripe listen` on a laptop and the production endpoint
never receive each other's events.

From the development/CI sandbox (Developers → API keys):

- `apps/api/.env`: `STRIPE_SECRET_KEY=sk_test_…` and `STRIPE_PUBLISHABLE_KEY=pk_test_…`;
- GitHub: `gh secret set STRIPE_SECRET_KEY` (CI then runs the Stripe contract tests on main).

Keep the production sandbox's keys for step 2.

## 1. Neon: the database

Create a project in **AWS us-east-1** (next to Render's Virginia region). From its connection details
copy two URLs, both with `?sslmode=require`:

- the **pooled** one (host contains `-pooler`): the API's `DATABASE_URL`;
- the **direct** one (no `-pooler`): `DIRECT_DATABASE_URL`, which migrations need.

## 2. Render: the API

New → **Blueprint** → this repository. `render.yaml` describes the service; fill in its variables:

| Variable                 | Value                                                                      |
| ------------------------ | -------------------------------------------------------------------------- |
| `DATABASE_URL`           | Neon's pooled URL                                                          |
| `DIRECT_DATABASE_URL`    | Neon's direct URL                                                          |
| `WEB_ORIGINS`, `WEB_URL` | the Vercel URL (step 3; a placeholder such as `https://example.com` first) |
| `STRIPE_SECRET_KEY`      | production sandbox, `sk_test_…`                                            |
| `STRIPE_PUBLISHABLE_KEY` | production sandbox, `pk_test_…`                                            |
| `STRIPE_WEBHOOK_SECRET`  | from step 5 (a placeholder `whsec_placeholder` until then)                 |
| `SMTP_URL`               | optional: without it, email is kept in the database (`sent_emails`)        |

`SIGNING_SECRET` is generated by Render; `PAYMENTS_ENV` is `production`. The API refuses to start in
production without the three Stripe values, and refuses live keys.

When it's up (`https://<service>.onrender.com/api/health` answers), load the catalog and create the store's
admin from a machine with the repository, against the direct URL:

```bash
DATABASE_URL="<Neon direct URL>" npm run db:seed -w @torra/api
DATABASE_URL="<Neon direct URL>" WEB_URL="<Vercel URL>" npm run admin:create -w @torra/api -- you@example.com "Your Name"
```

The second prints a one-time link (valid for an hour) that sets the admin's password.

## 3. Vercel: the web app

New Project → this repository, **Root Directory** `apps/web` (Next.js is detected; the npm workspace is
installed from the repository root). One variable, for builds and runtime:

- `API_ORIGIN` = the Render URL (`https://<service>.onrender.com`), no trailing slash.

## 4. Back to Render

Set `WEB_ORIGINS` and `WEB_URL` to the Vercel URL (`https://<project>.vercel.app`) and redeploy.

## 5. Stripe: the webhook (production sandbox)

Developers → Webhooks → Add endpoint:

- URL: `https://<service>.onrender.com/api/payments/webhook`;
- API version: `2026-10-28.endive` (the one the code pins);
- events: `payment_intent.succeeded`, `payment_intent.processing`, `payment_intent.payment_failed`,
  `payment_intent.canceled`, `charge.refunded`, `refund.created`, `refund.updated`, `refund.failed`,
  `charge.dispute.created`, `charge.dispute.updated`, `charge.dispute.closed`.

Copy its signing secret into Render's `STRIPE_WEBHOOK_SECRET` and redeploy. (Without it payments still
settle, through the order page and the sweep; with it, they settle at once.)

## 6. Checks

- The home page's "Entrar como cliente" opens a demo whose orders appear within seconds, two of them paid
  through Stripe (visible in the production sandbox's Payments).
- Paying the demo's waiting order with `4242 4242 4242 4242`, and again with `4000 0027 6000 3184`
  (3-D Secure), marks it paid; Stripe's webhook log shows 2xx deliveries.
- A refund from the demo's admin panel appears in Stripe, and the order shows it.
- The browser console shows no Content-Security-Policy violations on the order page.

The free API sleeps after 15 minutes without traffic; the first request then takes 40–60 s (the web app
says the server is waking up).
